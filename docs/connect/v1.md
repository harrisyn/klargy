# Klargy Connect v1

The contract between Klargy and an EMR (or any other system that sends people
into a queue). Klargy is the integrating side: it keeps every cross-reference
between its records and the EMR's, and it addresses EMR records by the EMR's
own IDs, so the EMR never has to store a Klargy ID.

Status of each part:

| Part | Phase | Status |
|---|---|---|
| Authentication, `/me`, self-registration, catalogues, mapping | 1 | This document, implemented |
| Queue entries by reference, event envelope with `refs` and `origin` | 2 | This document, implemented |
| Desk launch codes and `postMessage` protocol | 3 | This document, implemented |
| Patient lookup through the EMR, "you've joined" message, `statusUrl` and `position`, `GET /entries/by-ref` | 4 | This document, implemented |
| Journey automation: by-ref `service`, `transfer`, `priority`, appointment sync, analytics, pausing a service | 5 | This document, implemented |

Within v1 every change is additive: fields and events are added, never renamed
or removed.

Also: the [integration guide](./guide.md) (how a new EMR integrates, step by
step), [openapi.yaml](./openapi.yaml) (this contract as OpenAPI 3.1, with the
webhooks and the lookup call), the TypeScript package
[`@klargy/connect`](../../packages/connect) and the Python package
[`klargy-connect`](../../sdks/python/klargy-connect).

## 1. Authentication

An org admin creates an **integration** in Klargy (Admin, Integrations, EMR
connections). Klargy shows its API key once:

```
klg_live_3k9Q...   (prefix "klg_live_" + 40 random base62 characters)
```

Klargy stores only a SHA-256 hash and the first 12 characters (shown in the
admin list so people can tell keys apart). Every Connect call sends it:

```
Authorization: Bearer klg_live_3k9Q...
```

A key carries scopes. Every key gets all of these (keys made before a scope
existed are given it when Klargy is upgraded):

| Scope | Allows |
|---|---|
| `integration:write` | `PUT /integration` |
| `catalog:read` | `GET /catalog`, `GET /mappings` |
| `catalog:write` | `PUT /catalog` |
| `patients:write` | `PUT /patients/{id}` |
| `entries:read` | `GET /entries` |
| `entries:write` | `POST /entries`, `POST /entries/by-ref/…` |
| `desk:launch` | `POST /desk/launch` |
| `appointments:write` | `PUT /appointments/{appointmentRef}` |
| `analytics:read` | `GET /analytics` |

Errors use the usual Klargy shape, `{"error": "message"}` (phase 2 calls add a
machine-readable `"code"`, listed with each call), with 401 for a
missing, unknown or revoked key, 403 for a missing scope or when the
organisation's plan lacks the `emrIntegration` feature (that answer carries
`"feature": "emrIntegration"`). Each key may make 120 requests a minute; past
that Klargy answers 429 with a `Retry-After` header (seconds). Request bodies
are limited to 1 MB (413 above that).

Base URL: `https://<workspace>/api/v1/connect/v1`.

## 2. Endpoints (phase 1)

### `GET /me`

Checks the key. Used by the EMR's "Test connection" button.

```json
{
  "contract": "klargy-connect/v1",
  "organization": { "id": "…", "name": "Nyaho Medical Centre", "slug": "nyaho" },
  "integration": {
    "id": "…", "name": "Serenity", "status": "ACTIVE",
    "scopes": ["integration:write", "catalog:read", "catalog:write"],
    "registered": true,
    "catalogPublishedAt": "2026-10-14T13:05:00.000Z"
  }
}
```

### `PUT /integration`

Self-registration. The EMR tells Klargy where to send events and which origins
may embed the desk. Idempotent: call it on every save of the EMR's settings.

Request:

```json
{
  "system": { "name": "Serenity", "version": "2.0" },
  "webhookUrl": "https://api.example.com/v2/webhooks/queue/7d1f…",
  "lookupUrl": "https://api.example.com/v2/integrations/7d1f…/patient-lookup",
  "embedOrigins": ["https://emr.example.com"]
}
```

`webhookUrl` is required and must be a public `https` URL (plain `http` is
accepted outside production). `lookupUrl` and `embedOrigins` are optional
(phases 4 and 3). Setting `lookupUrl` turns on patient lookup (section 7);
leaving it out on a later call turns it off.

Response:

```json
{
  "integrationId": "…",
  "signingSecret": "whsec_…",
  "webhookEvents": ["entry.joined", "entry.called", "…"]
}
```

Klargy creates (or updates) one webhook endpoint owned by the integration,
subscribed to every event. `signingSecret` is that endpoint's secret; it is
returned on every call so the EMR can always recover it. Rotating the API key
in Klargy does not change it.

### `PUT /catalog`

The EMR publishes the records Klargy may map to. Replaces the previous
catalogue. Call it on save and whenever these records change.

```json
{
  "locations":     [{ "id": "…", "name": "Airport Clinic" }],
  "services":      [{ "id": "…", "name": "GP Consultation", "locationId": "…", "kind": "clinic" }],
  "servicePoints": [{ "id": "…", "name": "Consulting Room 3", "locationId": "…", "kind": "room" }],
  "practitioners": [{ "id": "…", "name": "Ama Owusu", "email": "ama@example.com" }],
  "registrationFields": [
    { "key": "first_name", "label": "First name", "required": true, "type": "text" }
  ]
}
```

All arrays are optional; IDs are the EMR's own and must be unique within
their array. Limits: 5,000 items per array and 1 MB per request. Response:

```json
{ "received": { "locations": 1, "services": 1, "servicePoints": 1, "practitioners": 1, "registrationFields": 1 } }
```

### `GET /catalog`

Klargy's own records, for EMRs that want to show them.

```json
{
  "locations":     [{ "id": "…", "name": "Airport Clinic", "externalId": "…" }],
  "services":      [{ "id": "…", "name": "GP Consultation", "locationId": "…", "externalId": null }],
  "servicePoints": [{ "id": "…", "name": "Consulting Room", "type": "CONSULTATION", "externalId": "…" }]
}
```

`externalId` is the EMR record the Klargy admin mapped it to, or `null`.

### `GET /mappings`

```json
{ "mappings": [{ "resourceType": "service", "klargyId": "…", "externalId": "…" }] }
```

Resource types: `location`, `service`, `service_point`, `staff`, and from
phase 2 `patient` (Klargy id is a patient user), `visit` (the EMR visit a
Klargy journey belongs to) and `encounter` (the EMR encounter a Klargy entry
belongs to). Phase 2 references are created by the calls below, never by the
admin.

Without a query this lists the admin's mappings (the four phase 1 types), as
in phase 1. `?resourceType=patient` (or any one type, including `appointment`
from phase 5) lists just that type; another value is 400.

## 3. Mapping

Mapping happens in Klargy (Admin, Integrations, the integration, Map). For each
Klargy location, service and service point the admin picks the matching record
from the published catalogue. Staff are matched by email automatically when
the desk is launched (phase 3); unmatched practitioners are registered as
staff then.

## 4. Webhooks

Delivered by Klargy's existing webhook system to `webhookUrl`:

```
POST <webhookUrl>
Content-Type: application/json
X-Webhook-Id: <delivery id>
X-Webhook-Event: entry.called
X-Webhook-Timestamp: 1791927099
X-Webhook-Signature: sha256=<hex HMAC-SHA256(signingSecret, "<timestamp>.<raw body>")>
```

Receivers must verify the signature over the exact raw body, reject a
timestamp more than 5 minutes from their clock, and de-duplicate on
`X-Webhook-Id` (a retry reuses it). Any 2xx is success; anything else is
retried 6 times over about 14 hours.

The admin's "Send test" button sends event `ping`.

Body:

```json
{
  "id": "<delivery id>",
  "event": "entry.called",
  "createdAt": "2026-10-14T13:05:00.000Z",
  "data": {
    "entryId": "…", "ticketNumber": "G012", "status": "SERVING", "queueId": "…",
    "service":  { "id": "…", "name": "GP Consultation" },
    "location": { "id": "…", "name": "Airport Clinic" },
    "servicePoint": { "id": "…", "name": "Consulting Room 3" },
    "journeyId": "…", "previousEntryId": null,
    "joinedAt": "…", "calledAt": "…", "servedAt": null, "completedAt": null,
    "patient": { "id": "…", "firstName": "Ama", "lastName": "Mensah", "phone": "…" },
    "statusUrl": "https://acme.klargy.com/status/<queueId>/<entryId>",
    "position": null,
    "origin": { "type": "staff", "integrationId": null },
    "refs": {
      "patient": "<EMR patient id>", "visit": "<EMR visit id>", "encounter": null,
      "service": "<EMR clinic id>", "location": "<EMR location id>",
      "servicePoint": null, "staff": "<EMR practitioner id>"
    }
  }
}
```

From phase 2:

- `refs` holds the EMR's own IDs for everything Klargy has a reference for,
  or `null`. It is only sent to the integration's own webhook endpoint (other
  endpoints in the organisation get no `refs`). `refs.staff` is the person
  who acted (who called or served), when they are mapped. Appointment events
  carry `refs` too, with what is known (`service`, `location`, `staff`, and
  `patient` on `appointment.created`).
- `origin.type` is `staff` (someone in Klargy), `public` (kiosk or the
  patient's phone), `integration` (a Connect call) or `system` (automatic,
  such as a service flow transfer). `origin.integrationId` is set for
  `integration`. **An EMR must ignore events whose `origin.integrationId`
  is its own integration id**: they echo its own calls.
- `origin` and `servicePoint` go to every endpoint. `servicePoint` is set on
  `entry.called` and later when the entry is being served at one, else
  `null`.
- `patient` also carries `identityData` (the identifiers Klargy holds).
  Events may carry extra fields for their kind (for example
  `entry.transferred` has `fromEntryId`, `fromServiceId`, `toServiceId`; a
  by-ref call with a `reason` adds `reason`); ignore what you don't use.
- New event `journey.completed` (data: `journeyId`, `completedAt`,
  `totalDuration` in minutes, `patient`, `origin`, `refs` with only `patient`
  and `visit`) when nothing in a journey is waiting or being served any more.
  It is sent once per closing; if the journey later gets another entry and
  closes again, it is sent again.

From phase 4, every entry object (entry events, and the entry in every
Connect response) also carries:

- `statusUrl`: the patient's live status page for the ticket, an absolute
  URL on the organisation's Klargy address. Safe to show or send to the
  patient: it shows the ticket, their place in line and the messages Klargy
  sent them, and needs no sign-in.
- `position`: their place in line (1 = next) while `status` is `WAITING`, in
  the order staff call people; `null` otherwise. It is the position when the
  object was made; use `GET /entries/by-ref` for a fresh one.

## 5. Queue entries (phase 2)

The queue follows the EMR **visit**, not the appointment: a walk-in has a
visit and no appointment, and gets a ticket all the same. One EMR visit is one
Klargy journey; each service the patient queues for during the visit is an
entry in that journey.

### `PUT /patients/{patientId}`

Creates or updates the Klargy patient for an EMR patient id. `POST /entries`
does the same inline, so this is only needed to update details.

```json
{ "firstName": "Ama", "lastName": "Mensah", "phone": "+233…", "email": null,
  "identifiers": { "mrn": "NMC-00123", "nationalId": "GHA-…" } }
```

`firstName` and `lastName` are required (at most 200 characters, like every
text field). A field left out is left as it is; `"phone": null` clears the
phone. `identifiers` (at most 20 keys, string or number values) are merged
into what Klargy already holds; `email` is kept with them. Klargy never emails
or signs in these patients: they get an internal placeholder login address,
not the EMR's email.

Response 201 when created, 200 when updated: `{ "patientId": "<EMR id>",
"klargyId": "…", "created": true }`. 400 for a missing or malformed field.

### `POST /entries`

Issues a ticket for an EMR visit. Send an `Idempotency-Key` header (at most
255 characters); the same key within 24 hours returns the first successful
response, with header `Idempotent-Replayed: true`. Only successful (2xx)
responses are kept, so a request that failed can be retried with the same key.
Reusing a key for a different request is 422 `IDEMPOTENCY_KEY_REUSED`; a
retry while the first is still running is 409 `IDEMPOTENCY_IN_PROGRESS`.

```json
{
  "refs": { "patient": "<EMR patient id>", "visit": "<EMR visit id>",
            "appointment": null, "encounter": null },
  "patient": { "firstName": "Ama", "lastName": "Mensah", "phone": "+233…" },
  "service": "<EMR clinic id>",
  "priority": 0,
  "notes": null
}
```

- `refs.patient`, `refs.visit` and `service` are required. `service` is the
  EMR id of a catalogue service the admin has matched; Klargy's own service id
  is also accepted.
- `patient` is required the first time Klargy sees `refs.patient`; when sent
  later it updates the details as `PUT /patients` does.
- If the visit already has a journey, the new entry joins it. If the visit
  already has an open (waiting or serving) entry for the same service, that
  entry is returned with status 200 instead of a new one.
- `refs.encounter`, when given, links the entry to that encounter (an
  encounter belongs to one entry; linking it again moves it).
  `refs.appointment` is accepted and not used yet.
- `priority` is a whole number from 0 to 100 (higher is called first);
  `notes` is free text shown to staff.
- The ticket goes into today's queue for the service (location time). When a
  new ticket is issued (201), Klargy sends the patient the "you've joined"
  message exactly as when they join from the kiosk or their phone: on their
  status page always, and by email and SMS as the organisation's
  notification settings say (Connect patients have no email address in
  Klargy, so in practice SMS when they have a phone number). It includes a
  link to their status page: "Your ticket for GP Consultation is G014. We'll
  let you know when your turn is close. Track your place: <statusUrl>". It is
  not sent for the 200 "already open" answer or a replayed request.
  "It's your turn" messages are sent as usual.

Response 201 (or 200 as above):

```json
{ "entry": { …the same object as webhook `data`, without `origin`… } }
```

The entry object (here, in by-ref responses and in `GET /entries`) is the
webhook `data` for an entry event, with this integration's `refs` and without
`origin` (which describes an event). `refs.staff` is always `null` in it.

Errors: 400 for a missing or malformed field; 404 `{"error": …, "code":
"SERVICE_NOT_MAPPED"}` when `service` has no match; 409 `QUEUE_CLOSED` when
today's queue is paused or closed (also when the service is switched off or
the organisation is paused); 422 `PATIENT_REQUIRED` when `patient` is missing
for an unknown patient; 403 when the plan's queue limits are reached
(`code: "LIMIT_REACHED"`, with `limitType`, `current`, `limit`); 409
`VISIT_PATIENT_MISMATCH` when `refs.visit` belongs to a different
`refs.patient`; 409 `ALREADY_IN_QUEUE` (with `entry`) when the patient already
has an open ticket in that queue under another visit.

### `POST /entries/by-ref/{type}/{id}/{action}`

Moves a ticket from the EMR side. `type` is `visit` (the visit's open entry:
the one being served, else the oldest waiting), `encounter` or `entry` (a
Klargy entry id). `action`:

| Action | Klargy status | From | Notes |
|---|---|---|---|
| `call` | `SERVING` | `WAITING` | Body may name `servicePoint` (EMR or Klargy service point id) |
| `complete` | `SERVED` | `WAITING`, `SERVING` | Runs the service's flow, so an auto-transfer issues the next ticket (event origin `system`) |
| `cancel` | `CANCELLED` | `WAITING`, `SERVING` | |
| `no-show` | `NO_SHOW` | `WAITING`, `SERVING` | |

Body (all optional): `{ "encounter": "<EMR encounter id>", "servicePoint": "…",
"staff": "…", "reason": "…" }`.

- `encounter` links the entry to that encounter for later
  `by-ref/encounter` calls (it is linked even when nothing else changes).
- `staff` is the EMR practitioner id of whoever is acting, for any action. A
  mapped practitioner is recorded as the actor (and sent back as
  `refs.staff`); an unmapped one is ignored.
- `servicePoint` on `call` picks the desk: the service point's desk for the
  entry's service where `staff` is signed in, else a free one, else the first.
  404 `SERVICE_POINT_NOT_MAPPED` when it matches nothing; 422
  `INVALID_SERVICE_POINT` when that service point doesn't serve the entry's
  service.
- `reason` (cancel, no-show) is recorded and sent in the event.

Moving an entry to the status it already has returns 200 and changes nothing
(`servicePoint` and `staff` are then ignored), so retries are safe. Response:
`{ "entry": { … } }`. 400 for an unknown `type` or `action`; 404
`ENTRY_NOT_FOUND` for an unknown encounter or entry; 404 `NO_OPEN_ENTRY` when
a visit has nothing open (or is unknown); 409 `INVALID_TRANSITION` (with the
entry's current `status`) for, say, completing a cancelled entry, or when
someone moved it first.

An `Idempotency-Key` header works here as on `POST /entries`. Use one (or
address the entry by `encounter` or `entry`) when retrying a `visit` call: once
the first `complete` has run, the visit's open entry may be the next ticket a
service flow issued, and a blind retry would complete that one.

### `GET /entries/by-ref/{type}/{id}`

Scope `entries:read`. The entry a by-ref action would move, without moving
it: `type` `visit` (the one being served, else the oldest waiting),
`encounter` or `entry`. Response 200 `{ "entry": { … } }` with a fresh
`position`. 404 `NO_OPEN_ENTRY` when a visit has nothing waiting or being
served (or is unknown); 404 `ENTRY_NOT_FOUND` for an unknown encounter or
entry (an encounter or entry is returned whatever its status); 400 for an
unknown `type`.

### `GET /entries`

`?updatedSince=<ISO time>` (required) `&visit=<EMR visit id>` (optional).
Entries in the organisation changed after that time (not only ones this
integration created), oldest change first, at most 500:
`{ "entries": [ … ], "nextUpdatedSince": "…" }`. For catching up after
downtime: call again with `nextUpdatedSince` until `entries` is empty. A full
page doesn't split entries changed at the same instant (unless more than 500
did), so none are skipped;
the same entry can appear on two pages if it changed again in between. An
unknown visit gives an empty list. 400 when `updatedSince` is missing or not a
time.

## 6. The desk inside the EMR (phase 3)

Consulting rooms are Klargy service points; the EMR doesn't need its own.
A practitioner signed in to the EMR opens Klargy's desk inside it, picks the
room they're working in (signing in to that service point), and calls and
moves patients from there. The EMR never sees a Klargy password.

### `POST /desk/launch`

Called by the EMR's server for the practitioner who is signed in to the EMR.

```json
{
  "staff": { "id": "<EMR practitioner id>", "name": "Ama Owusu", "email": "ama@example.com" },
  "servicePoint": null,
  "returnOrigin": "https://emr.example.com"
}
```

- `staff.id` and `staff.name` are required; `staff.email` is optional.
  Klargy finds the staff member by their existing `staff` mapping, else by
  email among the organisation's active staff (not patients), and records
  the mapping (an admin's mapping of that staff member to another
  practitioner is replaced), else registers them as service staff (role
  `SERVICE_STAFF`, using a staff seat) and records the mapping. A registered
  staff member's Klargy login is their email when nobody in Klargy has it
  yet, else an internal placeholder; the email is kept either way.
  Registered staff can't sign in to Klargy with a password or reset one;
  they only reach the desk through the EMR.
- `servicePoint` (EMR or Klargy id) preselects a room in the picker: the
  picker opens the room's location, lists its service first and focuses its
  first free desk. The practitioner still picks it.
- `returnOrigin` must be one of the integration's `embedOrigins` (compared
  as an origin, so a full URL on that origin is accepted). It is the only
  origin the desk will talk to.

Response 201:

```json
{
  "url": "https://<workspace>/widget/desk?launch=<code>",
  "expiresAt": "2026-10-14T13:06:00.000Z",
  "staff": { "klargyId": "…", "created": false }
}
```

`staff.created` is true when this call registered the staff member.

The code works once, within 60 seconds; Klargy keeps only a hash of it. Load
`url` in an iframe straight away. The desk signs the practitioner in with it
(a normal 24-hour staff session in the frame) and removes it from its
address. A used or expired code shows a message asking the practitioner to
open the desk from the EMR again: call `/desk/launch` again for a new one.

Errors: 400 for a missing or malformed field; 400 `ORIGIN_NOT_ALLOWED`; 404
`SERVICE_POINT_NOT_MAPPED` when `servicePoint` matches nothing; 403
`STAFF_INACTIVE` when the mapped staff member's Klargy account is switched
off; 403 `LIMIT_REACHED` (with `limitType: "users"`, `current`, `limit`) when
the plan has no staff seats left for a new registration.

Klargy serves `/widget/desk` with `Content-Security-Policy: frame-ancestors
'self' <origins>`, listing the `embedOrigins` of the organisation's active
integrations, so only those sites can frame it. An organisation with no
active integration (or none with `embedOrigins`) gets no such header, so the
desk embed script (`/embed/desk.js`) keeps working on any site; once an EMR is
connected, only the EMR's origins can frame the desk. Changes take up to a
minute to apply.

### Bar layout

Add `layout=bar` to the launch URL (`…/widget/desk?launch=<code>&layout=bar`)
to load the desk as one compact horizontal bar for a floating toolbar: the
room picker, who is being served, how many are waiting, and Call next,
Recall, Complete, No-show and Transfer (the last two become icon buttons
when the frame is narrower than about 1040px and move into a "More" menu
below about 860px; the row wraps below about 520px). The row is about 60px tall; menus and prompts open below it, so the
bar asks for more height with `klargy:resize` and the host sizes the frame
to it. The desk keeps `layout` in its address when it removes the code, so a
reload keeps the bar. Without `layout`, or with any other value, the desk
is laid out as before.

### Messages

The desk posts to its parent window, always with `targetOrigin` set to the
launch's `returnOrigin`, never `*`. Only a desk opened through a launch sends
these (it remembers the launch for the life of the browser tab, so a reload
keeps talking to the same origin):

| `type` | Other fields | When |
|---|---|---|
| `klargy:ready` | `contract` (`"klargy-connect/v1"`) | The desk has loaded and signed in (once) |
| `klargy:desk-changed` | `servicePoint`: `{id, name, externalId}` or `null` | Once after `ready` with the current room (or `null`), then whenever a room is picked, switched or left |
| `klargy:waiting` | `count` | When a room is picked and whenever the number waiting in its queue changes |
| `klargy:entry-called` | `entry` (the entry object, with `refs`) | The practitioner called someone |
| `klargy:entry-updated` | `entry` | The practitioner completed an entry, marked it as not here, or finished one left open at another desk; also for the new ticket when a patient is sent on to another service (by hand or by the service's flow) |
| `klargy:resize` | `height` (CSS pixels, a positive whole number) | Bar layout only: once it has loaded and whenever the height it needs changes (a menu or prompt opens or closes, a message appears). Size the frame to it, clamped to your own limits |

`servicePoint.id` is the Klargy service point (the room), `externalId` the
EMR's id for it (its `service_point` mapping) or `null`. `entry` is the same
object `POST /entries` returns, with this integration's `refs` (`refs.staff`
is `null`, as in that response). Messages are fire-and-forget: the webhooks
remain the record. New message types may be added within v1; ignore
types you don't know.

The parent may post to the desk (accepted only from `returnOrigin`, and only
from the parent window):

| `type` | Effect |
|---|---|
| `klargy:logout` | Leave the room and sign out of the desk (send when the practitioner signs out of the EMR). The desk sends `klargy:desk-changed` with `null` first, then shows that it has signed out. |

### Events

`servicepoint.opened` and `servicepoint.closed` webhooks, data
`{servicePoint: {id, name}, staff: {id, name}, origin, refs: {servicePoint, staff}}`,
when someone signs in to or leaves a room (one of its desks), from the desk
or anywhere else in Klargy:

- `opened` when someone signs in to a desk; going back to the desk you are
  already signed in to sends nothing. Taking over someone else's desk sends
  `closed` for them, then `opened`.
- `closed` when someone leaves a desk, an admin clears it, or an admin
  switches the desk off while someone is signed in.
- `staff` is the person who sat at the desk. `origin` is `staff` (the person
  who made the change, recorded in Klargy's audit log).
- As with every event, `refs` (the EMR's ids for the room and the staff
  member, or `null`) goes only to the integration's own endpoint.

## 7. Patient lookup through the EMR (phase 4)

Klargy asks the EMR who a patient is. The EMR searches its own records and
runs any insurance (cover) check; Klargy only shows the answer. Klargy never
stores the answer, except an identifier a patient typed on the join page.

### The lookup call (Klargy to the EMR)

Signed like a webhook, with the same signing secret (the one `PUT
/integration` returns):

```
POST <lookupUrl>
Content-Type: application/json
X-Webhook-Id: <new uuid per request>
X-Webhook-Event: patient.lookup
X-Webhook-Timestamp: <unix seconds>
X-Webhook-Signature: sha256=<hex HMAC-SHA256(signingSecret, "<timestamp>.<raw body>")>

{ "identifierType": "mrNumber",
  "identifier": "NH-004512",
  "context": "staff",
  "locationRef": "<EMR location id>" }
```

- `identifierType` is one of `mrNumber`, `memberNumber`, `phone`,
  `nationalId`, `passport`, `patientRef` (the EMR's own patient id, which
  Klargy knows from `refs`; staff only).
- `context` is `staff` (someone in Klargy) or `public` (the kiosk or the join
  page on a patient's phone).
- `locationRef` is the EMR's id for the Klargy location the lookup is for,
  when it is mapped; otherwise `null`.
- Klargy waits 5 seconds, does not follow redirects, only calls public
  addresses (plain `http` is allowed outside production) and never retries
  inside someone's request.

Answer 200 for staff:

```json
{ "matched": true,
  "patient": {
    "ref": "<EMR patient id>", "displayName": "Ama Mensah", "firstName": "Ama",
    "mrNumber": "NH-004512", "birthDate": "1988-04-02", "gender": "Female",
    "phoneMasked": "024••••19", "photoUrl": null,
    "identifiers": { "nationalId": "…", "passport": null, "memberNumber": "…" },
    "cover": { "payer": "…", "plan": "…", "memberNumber": "…",
               "status": "active", "expiresOn": "2027-01-31",
               "checkedVia": "payer", "message": null },
    "flags": ["has_open_visit", "outstanding_balance"] },
  "candidates": [] }
```

- No match: `{ "matched": false, "patient": null, "candidates": [] }`.
- A staff phone lookup that matches several patients: `matched: false`,
  `patient: null`, and up to 5 `candidates`
  `{ref, displayName, mrNumber, birthDate, phoneMasked}`.
- `cover` is `null` when there is no cover on file. `status` is `active`,
  `expired`, `inactive` or `unknown`; `checkedVia` is `payer` (asked the
  payer) or `records` (the EMR's own policy dates). A failed cover check is
  `status: "unknown"` with a `message`, never an error.
- Public context: only `{ "matched": true|false, "patient": { "firstName":
  "Ama" } | null, "candidates": [] }`. Klargy drops any other field it is
  sent, and never sends `patientRef` publicly.
- The EMR answers 401 for a bad, missing or stale (over 5 minutes) signature,
  400 for a bad body and 404 for an unknown or switched-off connection.
  Anything but a 2xx, or no answer in time, is a failed lookup.

### Where Klargy uses it

- **A data source.** While an active integration has a `lookupUrl`, the
  organisation has one data source of type `INTEGRATION` named
  "<integration name> lookup" (config `{integrationId}`), with field mappings
  `patient.mrNumber` to `mrNumber`, `patient.identifiers.memberNumber` to
  `memberNumber`, `patient.identifiers.nationalId` to `nationalId` and
  `patient.ref` to `emrPatientId` (added only when it has none, so an
  admin's changes are kept). It is switched off when `lookupUrl` is removed
  or the integration is revoked, and back on when it returns or the key is
  rotated. Admins can't create or edit it by hand.
- **Reception "Look up".** On a ticket's details, staff look the person up in
  the EMR: by the EMR's patient id when Klargy has one for them, else by
  phone. The answer fills in their details through the field mappings.
- **The desk.** While someone is being served and Klargy has the EMR's
  patient id for them, the desk shows the EMR's record (name, MR number, date
  of birth, gender, masked phone, cover and its expiry, flags), with expired
  or inactive cover clearly marked, and a box to check an MR or member number
  someone gives.
- **Kiosk and join page.** With the organisation setting "Require an MR or
  member number to join" (off by default) and an `INTEGRATION` data source,
  the join form asks for that number and Klargy looks it up with context
  `public` before issuing a ticket. Not matched: 422 `IDENTIFIER_NOT_MATCHED`
  and the form asks again. If the EMR can't be reached, the patient still
  gets a ticket and the entry's notes say "Identifier not verified". The
  number is kept with the patient's details either way.

### Staff endpoints (Klargy's own API, staff sign-in)

- `POST /api/v1/connect-lookup` `{ "identifierType": "mrNumber", "identifier":
  "NH-004512", "locationId": "<Klargy location id>" }` (`locationId`
  optional): the EMR's staff answer as above. 409 `LOOKUP_NOT_CONFIGURED`
  when no active integration has a `lookupUrl`; 502 `LOOKUP_FAILED` when the
  EMR fails or times out.
- `GET /api/v1/connect-lookup/entries/{entryId}`: the EMR's record for the
  patient on a ticket, by `patientRef`, as `{ "system": "<integration name>",
  "matched", "patient", "candidates" }`. 404 `NO_PATIENT_REF` when the
  patient isn't linked to an EMR record; 409 and 502 as above.

### Lobby screens

When a ticket is called, the lobby screen shows who is seeing them with the
room ("Dr Owusu, Consulting Room 3") when Klargy knows: the staff member
signed in at the desk, else the one who called them (a by-ref `call` with a
mapped `staff`). Practitioners Klargy registered from a desk launch carry the
name the EMR sent.

## 8. Journey automation (phase 5)

Lets the EMR move a patient from step to step (clinic, cashier, lab,
imaging, pharmacy) without anyone transferring them by hand, keep Klargy's
appointments in step with its own, and show queue numbers on its dashboards.
Everything here is additive.

### Department services in the catalogue

A catalogue service may carry `kind`: `clinic`, `lab`, `imaging`, `pharmacy`
or `cashier` (any other text is kept). An EMR without departments publishes
one service per location and department, for example
`{ "id": "<location id>:lab", "name": "Airport Clinic Laboratory",
"locationId": "<location id>", "kind": "lab" }`. Admins match them to Klargy
services like clinics; the matching screen groups the EMR's services by kind
and shows the kind of each match.

### Choosing a visit's entry by service

Every by-ref action (and `GET /entries/by-ref`, as `?service=`) on a `visit`
accepts an optional `"service"` in the body: an EMR or Klargy service id.
The visit's open entry is then chosen among that service's entries only (the
one being served, else the oldest waiting). 404 `SERVICE_NOT_MAPPED` when the
service matches nothing; 404 `NO_OPEN_ENTRY` when the visit has nothing open
there. It is ignored for `encounter` and `entry`.

### `POST /entries/by-ref/{type}/{id}/transfer`

Scope `entries:write`. Sends the patient on: completes the entry (`SERVED`)
and issues a ticket in today's queue of another service, in the same visit
(`previousEntryId` is the completed entry, `journeyId` is unchanged).

```json
{ "to": "<EMR or Klargy service id>", "service": "<narrows the visit's entry>",
  "priority": 50, "encounter": "<EMR encounter id>", "staff": "<EMR practitioner id>",
  "reason": "Lab orders" }
```

Only `to` is required. `priority` (0 to 100) defaults to the completed
entry's. `encounter` is linked to the new ticket. `staff` and `reason` are as
for the other actions. Klargy sends the new ticket the "you've joined" message
(with its `statusUrl`) and the event `entry.transferred` (with `fromEntryId`,
`fromServiceId`, `toServiceId` and `reason`); the completed entry gets no
`entry.served` event.

Response 201 `{ "entry": <new entry>, "from": <completed entry> }`. If the
visit already has an open entry in `to`, the response is 200
`{ "entry": <that entry>, "from": null }` and nothing changes, so retries and
repeated automation are safe. Errors: 400 without `to`; 404
`SERVICE_NOT_MAPPED` (`to` or `service`); 404 `NO_OPEN_ENTRY`,
`ENTRY_NOT_FOUND` as for the other actions; 409 `QUEUE_CLOSED` when `to`'s
queue isn't taking anyone; 409 `INVALID_TRANSITION` when the entry isn't
waiting or being served (or changed first); 409 `ALREADY_IN_QUEUE` (with
`entry`) when the patient already has an open ticket in `to` under another
visit; 403 `LIMIT_REACHED` as for `POST /entries`. `Idempotency-Key` works as
for the other actions.

### `POST /entries/by-ref/{type}/{id}/priority`

Scope `entries:write`. Body `{ "priority": 0-100 }` (required; `service`,
`encounter`, `staff`, `reason` as above). Sets the priority of the open
entry, which moves it in the waiting line (higher goes first); the line, the
lobby screens and the "almost your turn" messages update straight away.
Sends the new event `entry.priority_changed` (the entry, plus `priority` and
`previousPriority`). The same value returns 200 and sends nothing. Response
200 `{ "entry": { … } }`. 400 when `priority` is missing or out of range; 409
`INVALID_TRANSITION` when the entry isn't waiting or being served.

### `PUT /appointments/{appointmentRef}`

Scope `appointments:write`. Creates or updates the Klargy appointment for
the EMR's appointment `appointmentRef`:

```json
{ "refs": { "patient": "<EMR patient id>", "visit": null },
  "patient": { "firstName": "Ama", "lastName": "Mensah", "phone": "+233…" },
  "service": "<EMR clinic id>", "startTime": "2026-10-20T09:15:00Z", "endTime": "2026-10-20T09:30:00Z",
  "status": "booked", "staff": "<EMR practitioner id>", "notes": null }
```

- `patient` is needed the first time Klargy sees the patient, as for
  `POST /entries`. `refs.visit` and `staff` are accepted and not used yet.
- The times are the EMR's; they need not match Klargy's appointment slots,
  and the appointment holds no slot place.
- `status` is `booked` (default), `cancelled`, `no_show` or `completed`.
  Booked appointments get Klargy's usual reminder a day ahead (by email or
  SMS, per the organisation's settings). An appointment Klargy has already
  checked in stays checked in while the EMR says `booked`.
- Events (with `refs.appointment`, `patient`, `service`, `location`):
  `appointment.created` on create, `appointment.rescheduled` when the start
  time or service changes, `appointment.cancelled` when it becomes cancelled.
  Their data: `appointmentId`, `patientId`, `serviceId`, `startTime`,
  `endTime`, `status` (and `fromStartTime` on `appointment.rescheduled`).
  Appointments booked in Klargy itself send these events too, with
  `appointmentId` and slot times instead: `patientId` and `slotStart` on
  created and cancelled, `fromSlotStart` and `toSlotStart` on rescheduled.

Response 201 on create, else 200:

```json
{ "appointment": { "id": "…", "status": "booked", "startTime": "…", "endTime": "…",
  "service": { "id": "…", "name": "GP Consultation" },
  "refs": { "appointment": "<appointmentRef>", "patient": "…", "service": "…", "location": "…" } } }
```

`status` in responses may also be `checked_in`. Errors: 400 for a missing
`refs.patient`, `service` or `startTime`, a time that isn't ISO 8601, an
`endTime` before `startTime` or an unknown `status`; 404
`SERVICE_NOT_MAPPED`; 422 `PATIENT_REQUIRED`.

`POST /entries` accepts `refs.appointment` (the EMR appointment id): when it
is an appointment Klargy knows that is still booked, it is marked checked in
and Klargy sends `appointment.checked_in` (with the entry, and
`refs.appointment`). Any appointment event carries `refs.appointment` when the
appointment is linked.

### `GET /analytics`

Scope `analytics:read`. `?from=<ISO>&to=<ISO>&location=<id>&service=<id>`,
all optional. `location` and `service` accept EMR or Klargy ids. Without
`from` and `to`, the range is today in the location's timezone (the
service's location, else the location, else the organisation's first
location). The range is at most 90 days, counted by when people joined.

```json
{ "from": "…", "to": "…",
  "overall": { "joined": 42, "served": 35, "noShows": 2, "cancelled": 1, "noShowRatePct": 5.3,
               "avgWaitMinutes": 14.2, "medianWaitMinutes": 11, "p90WaitMinutes": 31, "avgServiceMinutes": 8.5 },
  "live": { "waiting": 7, "serving": 3, "longestWaitMinutes": 26 },
  "services": [ { "id": "<Klargy service id>", "ref": "<EMR service id>|null", "name": "GP Consultation",
                  "joined": 30, "served": 25, … } ] }
```

Minutes and the rate are `null` when there is nothing to measure. `live` is
now, across today's queues (each location's own today). `services` lists the
services with someone joining in the range, busiest first. Errors: 400 for a
bad time, `from` after `to` or a range over 90 days; 404 `SERVICE_NOT_MAPPED`
or `LOCATION_NOT_MAPPED`.

### `POST /services/{service}/status`

Scope `entries:write`. Pauses or reopens today's queue for a service (EMR or
Klargy id):

```json
{ "status": "PAUSED", "reason": "Clinic closed this afternoon",
  "message": "Dr Mensah's clinic is paused. Please wait at reception." }
```

`status` is `PAUSED` or `ACTIVE`. While paused nobody new joins (`POST
/entries` and `transfer` answer 409 `QUEUE_CLOSED`) and the patient's status
page shows that the queue is paused. On a pause everyone waiting gets one
message (in the app, and by email or SMS per the organisation's settings):
`message` (up to 300 characters), else "<service> is paused for now. Please
stay nearby; we'll let you know when it reopens." They get it once per pause.

Response 200:

```json
{ "queueId": "…", "status": "PAUSED", "changed": true,
  "service": { "id": "…", "name": "…" }, "location": { "id": "…", "name": "…" },
  "refs": { "service": "<EMR service id>", "location": "<EMR location id>" } }
```

Asking for the status the queue already has returns 200 with
`"changed": false` and does nothing else. 400 for another `status`; 404
`SERVICE_NOT_MAPPED`.

New events `queue.paused` and `queue.resumed` (data: `queueId`, `service`,
`location`, `reason`, `origin`, and `refs` with `service` and `location`)
are sent whenever a queue is paused or reopened, whether by this call or by
staff in Klargy. Closing a queue for the day sends neither.
